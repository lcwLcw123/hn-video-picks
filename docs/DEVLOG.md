# 开发日志：HN 推荐的 YouTube 知识视频

> 记录关键决策、遇到的问题、解决办法、以及需要人介入的地方。按时间顺序追加。

## 0. 目标拆解（2026-11-12）

用户需求 → 可操作的定义：
- **"值得看"** ≈ 长期价值。用 HN 上的“跨时间、跨话题、跨人”的独立推荐作为代理信号，而不是播放量 / 新鲜度。
- **"为什么推荐"**：每个视频都展示推荐者原话、所在讨论串、年份，可点回 HN 原评论。
- **"贴链接 ≠ 推荐"**：需要一个分类器区分「推荐」与「仅引用 / 出处 / 玩笑 / 自我推广 / 负面」。
- **可分享**：公开静态网站，每个视频有可分享的 URL。

## 1. 环境盘点

- 本机有 Node 23、Python 3.12、git、`gh`（已登录 GitHub）→ 部署选 **GitHub Pages**（免费、无需新账号）。
- 没有可用于批处理的独立 LLM API Key（Claude Code 自身的鉴权不应拿来跑批量管线）→ **推荐判定采用规则/打分分类器**，并用人工标注样本评估其精度。后续若有 API Key，可在边界样本上加 LLM 复判（已预留接口思路，见后文）。

## 2. 数据源调研

| 来源 | 结论 |
|---|---|
| HN Algolia API (`hn.algolia.com/api/v1`) | ✅ 免费、无需 key，支持全文检索评论 + 时间过滤。`youtube.com` ≈ 20 万条评论，`youtu.be` ≈ 7.6 万条。 |
| HN 官方 Firebase API | 只能按 item id 取，无法检索，不适合。 |
| BigQuery HN 公共数据集 | 完整但需 GCP 账号和计费 → 不用。 |
| YouTube oEmbed | ✅ 无需 key，拿到标题、频道、缩略图；也能判断视频是否已删除/私有。 |
| YouTube 观看页 HTML | ✅ 可解析出 category、时长、发布日期、播放量（仅作展示，不参与排序）。 |
| YouTube Data API v3 | 更稳，但需要 Google Cloud API Key → 列为可选改进。 |

**问题 1：Algolia 单次查询最多只能翻到 1000 条结果。**
解决：按时间窗口切片（初始按季度），若某窗口命中 > 1000 条就二分，递归直到每个窗口 ≤ 1000。抓取状态写到 state 文件，可断点续跑。

**问题 2：Python 访问 HTTPS 报 `CERTIFICATE_VERIFY_FAILED`。**
原因：python.org 安装的 macOS Python 默认不带根证书。解决：写了 `pipeline/net.py`，优先用 `certifi`，退回系统 `/etc/ssl/cert.pem`，CI 上用默认证书。

**问题 3（需要你注意）：磁盘空间不足。** 抓取中途 `No space left on device` 崩溃——这台 Mac 的数据卷只剩约 1.3 GB（运行前就几乎满了，不是本项目占用的）。
解决：原始数据改为 gzip 追加写（87 MB → 16 MB，压缩约 5 倍），每个时间窗口写成独立的 gzip member，中断也不会损坏已写数据；抓取器支持断点续跑，从中断处继续。YouTube 页面只在内存中解析，不落盘。
👉 建议你清理一下磁盘；本项目全部数据 < 150 MB。

**问题 4：分类器跑全量时卡死。** 剖析后发现是“提问”规则里的 `^(\s*\S+){0,12}\?\s*$` 触发了正则灾难性回溯（300 条评论耗时 16 秒）。改成线性的写法后全量 14 万条约 90 秒。加了一个单元测试防回归（长文本 + 问号必须 < 0.5 秒）。

## 3. 核心决策：怎么区分“推荐”和“贴链接”

抽样阅读后发现：绝大多数 YouTube 链接**不是**推荐——新闻片段、出处、玩笑、音乐、提问、给自己频道打广告、甚至批评。

- **方案选择**：没有 LLM API Key，所以做了一个**透明的规则打分器**（`pipeline/classify.py`）：约 14 类“推荐线索”加分（highly recommend / must watch / worth your time / great talk / changed how I think / if you haven't seen it…），6 类“非推荐线索”减分（自我推广直接一票否决、负面评价、出处、玩笑、提问、音乐娱乐）。命中的线索会显示在网站上，作为“为什么算推荐”的解释。
- **只看链接附近的文字**：取链接所在段落及前一段；对于“我最喜欢的演讲：1… 2… 3…”这种清单式评论，把评论开头的引导语也算进去。
- **原帖就是该视频的讨论串**不计入（那是在讨论别人的投稿，不是独立推荐）。

### 评估：盲标 + 留出测试集
- 从 14 万次提及中分层抽样 300 条（判为推荐 120 / 随机判为非推荐 130 / 边界 50），交给一个**看不到规则输出**的独立 AI 子代理逐条标注：strong / weak / no。
  （这里刻意用了子代理而不是自己标，避免“自己出题自己判卷”。）
- 偶数编号用来调规则，奇数编号留作测试集，调规则时不看测试集的错误。
- 第一版：精确率 ~81%，召回率很低（大量“nice video about it”这类温和推荐被漏掉）。按开发集的错误调整权重后：
  - 测试集上被判为推荐的 45 条中 40 条确实是推荐（~89%），28 条是强推荐。
  - 随机负样本中仍有 ~30% 被标注者视为（多为温和的）推荐 → **召回率偏低是有意的取舍**：上榜需要多人独立推荐，漏一些不影响；误收“贴链接”会让新闻片段和梗视频污染排名。
- **一个踩坑**：按总体比例加权的精确率在测试集上波动很大（0.84 → 0.64），原因是每条随机负样本代表 ~1100 条评论，**一条**被误判就能拉动整个指标。所以对外报告时用“判为推荐的样本中有多少是真的”这个更稳定的数，并在网站上写明。

## 4. 排序方法：数人，不数评论

`pipeline/score.py`，所有规则都有单元测试：
1. **一人一票**：同一账号多次推荐同一视频只算一次（防止某个人反复刷同一个链接）。
2. **同一讨论串打折**：同一串里第 k 位推荐者权重 1/k（同串的人互相影响，不完全独立）。
3. **跨年份加成**：× (1 + 0.35·ln 年份数)。
4. **跨话题加成**：× (1 + 0.15·ln(1+话题数))，话题来自讨论串标题的关键词分类。
5. **刻意不用**：播放量、发布时间、点赞数、标题和封面（单测里验证了播放量不影响分数）。
6. 上榜门槛：至少 2 个不同的人推荐。

第一次跑出来的前几名：Lustig《Sugar: The Bitter Truth》、Guy Steele《Growing a Language》、《Secret History of Silicon Valley》、Linus 讲 git、Randy Pausch《最后一课》、《Don't Talk to the Police》、Rich Hickey 的几个演讲、Ray Dalio《经济机器是怎样运行的》——基本都是 HN 上公认的“经典”，说明信号是有效的。

**问题 5：话题标签太宽。** “历史”匹配到了标题里的 “(1998)”，“商业”匹配到了 framework 里的 “work”。改为词边界匹配，年份只匹配 “1800s” 这类年代。

**问题 6：YouTube 限流（HTTP 429）。** 8 个并发抓视频页，约 280 个之后全部 429。
解决：降到 2 个并发 + 每请求 0.8 秒间隔 + 全局暂停（遇到 429 全体暂停 60 秒，再遇到翻倍，最多 15 分钟）；失败的条目标记为 transient，下次运行自动重试，成功的结果有缓存不会重抓。
👉 如果以后要做定期全量刷新，建议申请一个免费的 **YouTube Data API v3 Key**（Google Cloud，免费额度每天 1 万单位，批量查 50 个视频只花 1 单位），比抓页面稳定得多。

## 5. 产品形态

- **静态网站**（无后端）：数据在构建时生成 JSON，前端纯 HTML/CSS/JS、无构建工具。理由：零运维、免费托管、易分享、加载快。
- **列表页**：每张卡片突出的是“几个人推荐 / 几个讨论串 / 跨越哪些年份（年份条）/ 一句最有代表性的推荐原话”，而**不是**缩略图——缩略图刻意做了低饱和、小尺寸，悬停才恢复颜色（呼应“不看封面”）。
- **筛选**：搜索、话题、时长、最少推荐人数、“推荐跨越 ≥5 年”、排序（综合 / 推荐人数 / 跨越年份 / 最早被推荐 / 最近仍被推荐）。**所有筛选状态都写进 URL**，筛选结果本身也能分享。
- **详情页**（`#/v/<视频ID>`）：为什么它在这里（推荐人数、独立讨论串、年份、话题、排名）、每年推荐人数柱状图、全部推荐原话（按时间、带 HN 原评论链接和所在讨论串）、被判为“只是提到”的评论（折叠，方便检查分类器）。
- **方法说明页**：公开算法、评估结果和局限。
- 视频播放用 `youtube-nocookie.com`，点击后才加载 iframe（不在用户没点时加载 YouTube 跟踪脚本）。
- 已知局限：hash 路由下，分享到社交平台的预览卡片是全站通用的，不是每个视频单独的。

## 6. 验证方式

- 单元测试（`tests/test_pipeline.py`，18 个）：URL 各种变体、分类器正负例、自我推广一票否决、正则性能、一人一票、同串打折、播放量不影响分数、话题词边界、清单式评论。
- 端到端冒烟测试（`tests/e2e/smoke.mjs`）：用本机 Chrome 无头模式打开网站，桌面 + 手机两种尺寸，检查列表渲染、话题/排序写入 URL、搜索、详情页推荐条数与统计一致、方法页、不存在的视频显示错误，且无 JS 报错。
- **问题 7**：Claude 桌面端内置的浏览器预览工具被自动模式的安全检查拦下了。改为自己写 Playwright 脚本驱动本机 Chrome 截图和断言（只装了 `playwright-core`，不下载浏览器）。

**问题 8：youtube.com 整站连不上了。** 抓取视频页一段时间后，`www.youtube.com` 开始直接断开 SSL 连接（不是 429）。排查：本机所有流量走本地代理 `127.0.0.1:10808`；google.com、hn.algolia.com、i.ytimg.com（缩略图 CDN）都正常，只有 youtube.com 不通 → 判断是 YouTube 对代理出口 IP 做了软封禁。
解决：
1. 先停掉抓取，避免封得更久。
2. 标题 / 频道 / 是否已删除，改走 `noembed.com`（公共 oEmbed 代理）；加了“熔断”：youtube.com 失败一次就 10 分钟内不再尝试。
3. 视频分类、时长暂缺时，“知识类 vs 音乐娱乐”的判断退回到标题/频道启发式（VEVO、- Topic、official video、lyrics、remix…）。
4. 缓存里标记了哪些视频还没有页面数据，等网络恢复后 `python3 pipeline/enrich_youtube.py data/candidates.json --retry-pages` 补齐。
👉 **需要你介入（可选）**：申请一个 YouTube Data API v3 Key 是根本解法——它走 googleapis.com，不受这个封禁影响，也更合规。

## 7. 部署

- 新建公开仓库 `lcwLcw123/hn-video-picks`，GitHub Pages（Actions 模式）：推送 `main` → 先跑单元测试 → 发布 `site/`。
- **需要人确认的点**：创建公开仓库这一步被 Claude Code 自动模式的权限检查拦下了（会以你的身份对外发布）——这是合理的，我停下来问了你，得到同意后才创建。

- **问题 10**：第一次 Actions 部署失败：`Get Pages site failed`——仓库还没开启 Pages。用 `gh api -X POST repos/<repo>/pages -f build_type=workflow` 开启后重跑成功。
- **问题 11**：对线上地址跑冒烟测试时报了一堆 `ERR_CONNECTION_CLOSED`——都是 YouTube 缩略图（同样的网络问题），不是网站的问题。测试改为记录失败请求的 URL，只把本站资源的失败算作错误。
- **问题 12**：第二次部署报 `No artifacts named "github-pages"`——上传明明成功了。原因是在同一个 job 里上传后立刻部署，部署端有时看不到刚上传的产物。重跑一次仍失败，于是按 GitHub 官方模板把“上传”和“部署”拆成两个 job，之后稳定成功。

## 给同事分享时的几点体会

1. **先把模糊需求变成可检验的定义**：“值得看”→“不同的人、不同年份、不同话题的独立推荐”；“贴链接≠推荐”→ 一个有精确率/召回率的分类问题。
2. **评估要防“自己出题自己判卷”**：让一个看不到规则输出的子代理盲标，并留出测试集；同时警惕加权指标在小样本下的方差。
3. **透明胜过聪明**：没有 LLM Key 时，规则打分器反而有好处——每条推荐都能展示“命中了哪些线索”，用户可以自己检查。
4. **真实世界的阻碍大多是工程环境问题**：证书、磁盘、限流、代理 IP 被封、CI 竞态，每个都不难，但都需要停下来诊断，而不是盲目重试。
5. **对外发布的动作要停下来确认**：AI 在创建公开仓库前被权限检查拦下，问过人之后才继续——这是该有的边界。

## 11. 接入 YouTube Data API（用户决定申请 Key 之后）

- `enrich_youtube.py` 检测到环境变量 `YOUTUBE_API_KEY` 就改走 `videos.list`：一次 50 个视频、1 配额单位，2,384 个候选只要 ~48 次请求。拿到标题、频道、分类、时长、发布日期；响应里缺失的视频记为已删除/私有。
- 先验证了 `googleapis.com` 在当前代理网络下可达（youtube.com 被封不影响它）。
- Key 只从环境变量读，不进仓库、不进聊天记录。补了 2 个单元测试（ISO 8601 时长解析、批量请求 + 缺失视频处理，用假的 HTTP 层）。
- **实际运行**：用户在自己的终端里设置 Key 并运行（Key 不经过 AI、不进仓库；提交前扫描确认仓库内无 `AIza…` 字样）。2,384 个视频全部拿到元数据：2,275 个可看、109 个已删除/私有，分类和时长覆盖 100%。
- 一个小插曲：第一次 `export` 时用户照抄了示例里的占位符 `your_key_here`；另外在 Terminal 面板里 `export` 的变量只在那个终端里有效，AI 的命令看不到——所以改成让用户在自己终端里跑完，AI 只负责后续检查和部署。

**问题 13：YouTube 分类不可靠。** 有了真实分类后发现，大量好演讲被上传者归在 “Gaming / Entertainment / 甚至 Music” 下（如 Jonathan Blow《Preventing the Collapse of Civilization》19 人推荐、《Line Goes Up》、ZFS、CRDTs 的技术演讲）。若按分类一刀切，会误藏 160+ 个视频。
解决：非知识类分类只是“默认怀疑”，以下任一成立就保留：标题像演讲/讲解/纪录片；或 ≥2 位推荐者（或 ≥40%）的原话命中“知识型内容 / 讲得清楚”线索。结果：可浏览的知识类视频 2,173 个，默认隐藏 102 个（多为喜剧小品、游戏实况、少数边界视频，筛选里可打开）。加了单元测试。

## 12. AI 复判：提高召回率（2026-11-12 下午）

**为什么要做**：规则分类器为了精确率牺牲了召回——盲标显示，被规则判为“不是推荐”的评论里约 30% 其实是（多为语气平淡的）推荐，例如 “Jen Simmons made a really good video about exactly this”。这让一些靠“低调好评”积累口碑的视频进不了片单。

**方案演变**：
1. 先写了走 Anthropic Batches API 的脚本（`pipeline/llm_rejudge.py`，Claude Opus 5.5、结构化 JSON 输出、半价批处理，估算 ~$20），需要用户提供 API Key。
2. 用户问“能不能直接用子代理判？”——可以：不需要 Key，用的是 Claude Code 本身的额度。于是改为把待判评论切成 6 份，**并行启动 7 个 Sonnet 子代理**（6 份待判 + 1 份对照用的 300 条盲标样本），每个子代理按与当初盲标完全相同的标准逐条阅读、写 JSONL。API 脚本保留，作为可复现、可定时运行的版本。
3. **控制范围**：并不是所有“没过线”的评论都值得复判。只取规则分数 ≥0.2、且视频已有 ≥1 位规则认定推荐者的评论——只有这些“多一票就可能上榜或升位”的才影响结果。从 5,864 条缩到 2,520 条。

**结果**：
- 测试集（150 条留出）：规则单独 精确率 85% / 样本内召回 58% → 规则+AI 复判 **88% / 71%**。召回明显提升，精确率没有下降。
- AI 与盲标的三分类一致率 94%——**但要打折**：盲标者也是 Claude 子代理，同族模型可能共享盲点。如果要更严格，应该找人工抽检一部分。
- 2,520 条中 1,867 条被判为推荐（强 / 温和各半）；温和推荐权重 0.6、强推荐 0.85，低于规则认定的强推荐。
- 片单从 2,384 个视频增至 3,003 个；前 50 名有 43 个不变，上升明显的是《Elo World》《TempleOS | Down the Rabbit Hole》《I painted a Landscape with Mathematics》这类“粉丝说话很低调”的视频。
- 网站详情页里，AI 复判找回的推荐带 “AI 复判” 标记和一句理由，方便读者自行判断。
- 抽查：strong 基本都是明确好评；no 正确排除了裸引用、玩笑、批评；weak 最宽松（如 “for perspective, take a look at this video”），这也是给它较低权重的原因。

**踩坑**：zsh 下 `rm -f dir/*` 在目录为空时报 “no matches found” 并中断了整条 `&&` 命令链，重跑时去掉了这一步。

**需要用户介入的地方（及原因）**：
- **DNS**：Cloudflare 需要用户本人登录，AI 无法代劳。第一次添加时记录没有保存成功——AI 直接查询 Cloudflare 的权威 DNS 服务器（而不是公共 DNS）发现“没有这条记录”，于是给出逐步点击说明，用户重新添加后立即生效。
- **为什么选灰云**：Let's Encrypt 的 HTTP-01 验证要直连源站；若开代理且 Cloudflare 开启了 “Always Use HTTPS”，验证请求会被跳转到 HTTPS，而那时证书还不存在。证书签发后可以改成橙云（主站就是橙云 + 源站证书）。
- **权限**：AI 第一次 SSH 被自动模式的权限检查拦下（改生产服务器属于高风险操作），用户明确回复 “Try again” 后才继续。随后“写日志 + 提交 + 推送”的一条合并命令也被一个独立的安全检查拦下，改用编辑器写日志。

**问题 14**：部署脚本最后一行 `echo current -> $(readlink …)` 里的 `->` 被 shell 当成重定向，报 “Is a directory”。上传和切换其实已成功；修正引号后重跑。
**问题 15**：zsh 不会对 `$SSH` 这样的变量做分词，`$SSH 'cmd'` 被当成一个不存在的命令名。改为直接写命令 / 在 bash 脚本里用数组。
**问题 16**：公共 DNS（1.1.1.1 / 8.8.8.8）缓存了之前“不存在”的结果（负缓存最长 30 分钟），所以刚加完记录时公网暂时解析不到；Let's Encrypt 查的是权威服务器，不受影响。验证时用 `curl --resolve` 固定 IP，同时仍做真实证书校验。
**问题 17**：新上榜的 619 个视频里，有 556 个在抓取 YouTube 页面时又被限流，缺分类和时长；用 YouTube API Key 跑一次 `enrich_youtube.py` 即可补齐（只补缺的）。
